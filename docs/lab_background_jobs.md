# Фоновые запросы лаборатории

Схема `LabGenerationJob` (миграция 0033) сохраняет отправленное сообщение, исходную
версию, пользователя, режим, состояние, результат и ошибку. POST `lab/jobs/`
возвращает подтверждение после записи в БД и запуска отдельного процесса
`manage.py run_lab_job <uuid>`. AI выполняется вне HTTP-запроса браузера.

Worker использует существующие проверки прав, лимиты, учёт расходов и генератор.
Повторная доставка одного job безопасна: условное обновление queued → running
выигрывает только один процесс. Одновременно разрешён один активный запрос на
пользователя и на проект. Для повторной попытки после ошибки нужен новый явный
запрос пользователя; автоматического платного повтора нет.

Страница читает первоначальный статус с сервера, затем опрашивает endpoint
`lab/jobs/status/`. Во время создания сайта показывает кузницу Бруно на всём
предпросмотре. Обсуждение оставляет предпросмотр доступным. После завершения
страница открывает сохранённую версию/историю. Ошибки и исходный текст запроса
сохраняются при переходе, обновлении или повторном входе.

Процесс отделён от веб-сервера; его работа не зависит от закрытия вкладки и
перезапуска веб-процесса. Heartbeat и PID позволяют показать ошибку при смерти
worker. Живой процесс после сна компьютера не отменяется по старому heartbeat.
Перезагрузка ОС/остановка самого worker прерывает текущий вызов модели: статус
станет ошибкой, а платный вызов автоматически повторяться не будет.

В локальном запуске используется Python текущего окружения. На сервере необходимы
права на запуск management command и общая БД/каталог проекта. Незавершённые queued
задачи безопасно доставляются повторно при запросе статуса. Журнал доверенного
обработчика: `.runtime/lab-jobs.log`; исходники сгенерированных сайтов по-прежнему
выполняются отдельным изолированным runtime и не получают прав worker.

Проверки: `manage.py test founder.test_lab_jobs` и `node --test tests/lab_jobs.test.cjs`.
