# Общий сервер BrunoHost

Лаборатория может собирать сайты с регистрацией, ролями, формами, фотографиями, связанными записями и бронью ресурса на интервал. У каждого сайта свои разделы, набор полей, права, подписи и тема оформления. Сервер исполняет заранее проверенные действия. Для произвольного Python и индивидуального интерфейса у лаборатории остаётся изолированный генератор. Статические версии продолжают работать.

## Как проверить на тестовом стенде

1. Подключите отдельную тестовую PostgreSQL через `DATABASE_URL`. У роли приложения должны отсутствовать `SUPERUSER` и `BYPASSRLS`. Для запуска набора тестов Django этой роли также нужна возможность создать тестовую базу.
2. Установите `BRUNOHOST_SHARED_ENABLED=1`. Настройте `BRUNOHOST_BASE_URL` на адрес BrunoHost. Для локального теста подойдёт `http://localhost:8000` при включённом DEBUG. Режим `BRUNOHOST_PATH_MODE=1` позволяет открыть сайт по пути `/sites/<адрес>/`. На публичном стенде используйте HTTPS.
3. Выполните команды из корня репозитория.

```sh
python manage.py migrate
python manage.py check_shared_host
python manage.py test founder.test_shared_host founder.test_hosting founder.test_lab_costs
```

4. Чтобы посмотреть результат вручную, откройте «Лаборатория сайтов». Пример задачи для обычного чата — «Создай трекер дефектов: рабочий регистрируется, выбирает комнату и прикладывает фото. Прораб видит все дефекты и назначает ответственного». Генерация в обычном чате использует настроенного провайдера и расходует токены. Автотесты выше подставляют фиксированные ответы.
5. Откройте предпросмотр. В настройках версии рядом с ним видны таблицы и поля. Зарегистрируйте пользователя на сайте. Владелец проекта может назначить ему роль по логину в настройках версии, отдельно для предпросмотра и опубликованного сайта. Посетитель при регистрации получает роль `member`.
6. Опубликуйте версию через BrunoHost. Создайте запись на публичном адресе, добавьте через лабораторию необязательное поле, затем опубликуйте обновление. Старая запись и её фотография должны остаться доступными. Новое поле можно заполнить при редактировании.

## Где находятся данные

Общие таблицы PostgreSQL содержат пространства сайтов, аккаунты, записи с JSONB, фотографии и брони. Содержимое фото хранится в отдельной таблице в бинарном виде. Запись хранит идентификатор файла. Одна согласованная копия PostgreSQL включает и записи, и фотографии. Размер фото, стоимость диска и резервных копий продолжают расти с загрузками.

У опубликованного проекта постоянное пространство. Каждая версия предпросмотра получает отдельное пустое пространство. Все предпросмотры проекта делят один бюджет. Отдельный бюджет действует для публикации. По умолчанию в каждом бюджете до 1 000 аккаунтов, 20 000 записей, 20 000 файлов и 64 МиБ фотографий. Лимит изображения 4 МиБ, форматы JPEG, PNG и WebP. Размер данных одной записи ограничен 16 КиБ. Квоты резервируются в транзакции. В этих технических ограничениях не заложена цена подписки.

Структура использует постоянные ключи полей с изменяемыми подписями. Добавление необязательных полей и расширение вариантов выбора совместимы с прежними записями. Удаление таблицы или поля, сужение вариантов, смена типа или правила брони требуют явного переноса. Ошибка до фиксации релиза сохраняет прежнюю публикацию. Перед сохранением версии и перед переключением публичного адреса сервис проверяет открытие страницы и отказ анонимному запросу сведений об аккаунте.

## Доступ и нагрузка

Параметр поля `write_roles` ограничивает его изменение выбранными ролями, в том числе при создании записи. Это позволяет рабочему добавить дефект и фотографию, а право назначить ответственного оставить прорабу. Сервер проверяет ограничение при каждом сохранении.

BrunoHost выводит сайт из публичного адреса или из проверенного доступа к проекту в лаборатории. Сервер проверяет сессию посетителя и права на действие. Для каждой таблицы задаются создание, чтение своих или всех записей и изменение своих или всех записей. Файл может прочитать загрузивший его пользователь или участник с доступом к записи, где он прикреплён. Аккаунты платформы и посетителей сайта независимы.

Принудительные политики PostgreSQL ограничивают строки текущим пространством. Составные внешние ключи защищают связи владельцев и броней между пространствами. Исключающее ограничение PostgreSQL защищает пересекающиеся брони даже при конкурентной записи. Интервалы допускают начало следующего занятия точно в момент окончания предыдущего.

В общем режиме модель описывает интерфейс и данные. HTML формирует шаблон платформы, операции выполняет общий API. Вход, чтение, сохранение, скачивание и бронирование обходятся без обращения к AI. Для нового проекта с неподдерживаемой бизнес-логикой диспетчер может выбрать генерацию отдельного сервера. При несовместимой правке существующего общего сайта лаборатория сообщает о необходимости переноса. Произвольный код модели нельзя запускать на основном веб-сервере.

## Выкладка и аварийное восстановление

- Для пилота задайте непустой список проектов в `BRUNOHOST_BACKEND_PROJECTS`. Пустой список разрешает публикацию любому проекту, у которого уже есть право редактировать сайт. Автоматического списания за хостинг и проверки числа оплаченных мест в этом обработчике нет. Перед общей платной продажей привяжите публикацию к условиям действующего тарифа.
- Согласуйте максимальный размер запроса на прокси с квотой изображения. Для фото по 4 МиБ прокси должен пропускать запрос такого размера. Проверьте загрузку через публичный адрес пилота.

- Изменения зависят от миграции `0044_lab_plan_period`, уже находившейся в рабочем дереве. Она должна войти в выкладку вместе с зависимостями. Миграции `0045` и `0046` добавляют общие структуры и политику изоляции.
- Если основной BrunoLab пока работает на SQLite, переключение одной переменной на пустую PostgreSQL откроет пустую базу платформы. Сначала перенесите данные самой платформы на отдельном стенде и сверьте аккаунты, проекты, версии и расчёты. Пример импорта ниже относится только к данным сгенерированного сайта.
- На PostgreSQL выполните миграции, затем `check_shared_host` под ролью, с которой работает веб-приложение. Запустите приложение и обработчик лаборатории с согласованными настройками. Существующий список `BRUNOHOST_BACKEND_PROJECTS` позволяет ограничить публикацию выбранными проектами. Для приостановки новых сборок и публикаций установите `BRUNOHOST_SHARED_ENABLED=0`. Уже опубликованные общие сайты продолжают работать при доступной PostgreSQL.
- Для общего резервного копирования запланируйте запуск следующего скрипта под отдельной учётной записью PostgreSQL с правом полного чтения, включая строки под RLS. Подключение передаётся через стандартную конфигурацию libpq. Каталог назначения должен быть закрыт от посетителей.

```sh
PGSERVICE=brunohost_backup deploy/brunohost/backup-shared.sh /private/backups
```

Скрипт создаёт архив `pg_dump` всей базы, проверяет его оглавление и только после этого перемещает готовый файл на место. Для защиты от потери сервера копию нужно отправлять в отдельное хранилище, задать срок хранения и проверять восстановление. Для учебного восстановления используйте только отдельную пустую базу.

```sh
pg_restore --exit-on-error --dbname=brunohost_restore_test /private/backups/имя-архива.dump
```

Роли сервера, конфигурацию, ключ Django, файлы старых изолированных сайтов и прочие внешние загрузки платформы обслуживайте отдельно. Расписание резервных копий и внешнее хранилище на продакшене этим изменением не настраиваются.

## Перенос проверенного проекта SQLite

Команда переносит одну явно сопоставленную таблицу в пустой предпросмотр. Входной файл — согласованный снимок SQLite, полученный через SQLite backup или после остановки записи. Поддерживаются простые поля и фотографии в BLOB. Для импортированных записей создаётся служебный владелец с отключённым входом. Оператор сверяет число записей и файлов. Повтор с тем же снимком и сопоставлением возвращает «уже перенесён». При ошибке вся операция откатывается.

```sh
python manage.py import_shared_sqlite --site-version UUID --snapshot /private/test.sqlite3 \
    --table items --collection defects --field room=name --field photo=picture
```

Проверены перенос из работающего тестового SQLite-сайта и отдельный пример с фотографиями. Аккаунты, пароли, произвольные связи, обособленные файлы на диске и переключение действующего клиентского сайта требуют индивидуальной миграции.

## Воспроизводимый замер

На macOS с доступным штатным изолированным исполнителем и тестовой PostgreSQL:

```sh
python manage.py test founder.benchmark_shared
```

Один прогон на Apple M5, macOS 26.5.1, PostgreSQL 16.2, Django 6.0.8. На каждый режим создано три сайта обычным потоком генерации с подставными ответами моделей. На каждом сайте выполнено 20 пар «добавить запись / прочитать список». Замер идёт через гостевой обработчик Django на прогретом приложении. Клиент тестовый, без сетевой задержки до посетителя. Изолированный вариант проходит через реальный локальный HTTP-процесс SQLite. Эталонный SQLite-сервер минимален, а общий дополнительно проверяет роль и сессию. Регистрация и сборка сайтов в замер задержки не входят.

| Метрика | Общий BrunoHost | Изолированный SQLite |
| --- | ---: | ---: |
| Запросы / ошибки | 120 / 0 | 120 / 0 |
| Медиана | 4,46 мс | 39,94 мс |
| 95-й процентиль | 5,10 мс | 50,54 мс |
| Дополнительные процессы сайтов | 0 | 3 |
| Сумма RSS этих процессов после нагрузки | 0 | 106,98 МиБ |
| RSS процесса теста до / после | 186,89 / 187,23 МиБ | 187,23 / 204,62 МиБ |
| Сумма RSS процессов тестовой PostgreSQL до / после | 59,94 / 61,36 МиБ | 61,36 / 61,78 МиБ |
| Вызовы подставного провайдера при создании трёх сайтов | 6 | 9 |
| Записи расхода AI на действия посетителей | 0 | 0 |

RSS включает общие страницы памяти. Строки о процессах и PostgreSQL нельзя складывать для оценки физического потребления машины. Режимы измерены последовательно в одном процессе теста. Выигрыш в числе вызовов при создании относится к сравнению с включённой двухэтапной сборкой SQLite. Суммы токенов и рублей у действующего провайдера этим тестом не измеряются. Ёмкость в тысячи одновременно активных сайтов требует отдельной нагрузки с реальным распределением посетителей, фото и частоты записей. Запись в пределах одного сайта и резервирование квот проекта сериализуются.
