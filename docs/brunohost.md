# BrunoHost: публикация из лаборатории

Ветка BrunoHost. Публикация независима от карточки сообщества и её видимости.
Для сайтов с общими формами, ролями, файлами и бронью предусмотрен отдельный режим на PostgreSQL. Подключение, проверка и замеры описаны в [инструкции по общему BrunoHost](brunohost-shared.md).
В лаборатории выбранную HTML-версию или приложение `generated` можно опубликовать,
обновить и снять с публикации. Адрес вида `h` + 13 случайных букв/цифр сохраняется.
Черновики не обновляют публичную версию автоматически. Посетителю аккаунт BrunoLab
не нужен. Старые версии с готовыми Django-модулями пока не публикуются: интерфейс
объясняет ограничение, вместо того чтобы выдавать макет за рабочее приложение.

## Локально

`BRUNOHOST_BASE_URL=http://localhost:8000` (по умолчанию при DEBUG).
Адреса `h….localhost:8000` открываются в Chrome без редактирования hosts.
Django остаётся доступен на `127.0.0.1:8000` и `localhost:8000`.
На macOS серверный код запускается через deny-by-default `sandbox-exec`.
Для других ОС автоматического небезопасного запуска нет.

## Подключение в интернете

Нужны отдельный домен для пользовательских сайтов (например `brunohost.example`),
wildcard DNS `*.brunohost.example` на сервер и wildcard HTTPS-сертификат.
Домен приложения BrunoLab и домен BrunoHost должны быть разными. Публикация по пути
на основном домене намеренно не используется. Основные cookies оставлять host-only,
не задавать общий SESSION_COOKIE_DOMAIN/CSRF_COOKIE_DOMAIN.

Переменные сервера:

```
BRUNOHOST_BASE_URL=https://brunohost.example
BRUNOHOST_PATH_MODE=0
BRUNOHOST_ROOT=/data/brunohost
BRUNOHOST_ENGINE=docker
BRUNOHOST_DOCKER_IMAGE=brunohost-worker:1
BRUNOHOST_MAX_RUNNING=5
DJANGO_TRUST_PROXY_HTTPS=1
```

Включать доверие к X-Forwarded-Proto только за своим proxy, который перезаписывает
этот заголовок. Не открывать Django напрямую из интернета.

Сборка подготовленного образа на Linux-сервере с Docker:

```
docker build -t brunohost-worker:1 -f deploy/brunohost/Dockerfile .
python manage.py migrate
```

Reverse proxy передаёт wildcard-запросы тому же Django-процессу, сохраняя Host и
выставляя `X-Forwarded-Proto: https`. Ограничить тело запроса 1 МБ и настроить
серверные лимиты соединений. `ALLOWED_HOSTS` основного приложения не расширять до
`*`: middleware BrunoHost самостоятельно проверяет хост до авторизации и маршрутов.
Не отдавать файлы BRUNOHOST_ROOT через nginx/WhiteNoise.

Статические сайты не требуют исполнителя. Для серверных нужен доступ доверенного
процесса к Docker и указанному образу. Контейнер каждого сайта: без сети и портов,
rootfs read-only, без capabilities, no-new-privileges, 256 МБ памяти, 0.5 CPU,
32 процесса. HTTP передаётся по отдельному Unix-сокету, который доступен только
этому контейнеру и серверу. Docker socket и окружение BrunoLab внутрь не передаются.
На текущей Amvera установка Docker внутри web-контейнера не предполагается:
потребуется подходящий отдельный сервер/исполнитель и домен. Текущий production
не обновлялся; без подключения исполнителя серверная публикация отключена.

## Бета для одного демонстрационного проекта

Для проверки без переноса действующего сайта разверните отдельный экземпляр
BrunoLab на одном Linux VPS. У экземпляра отдельные настройки, секреты и
постоянное хранилище. Лаборатория и публичные сайты должны попадать в один
экземпляр Django, чтобы публикация и гостевые запросы использовали одну базу и
одни и те же файлы. Простое перенаправление DNS на VPS без этого не подключает
публикацию из текущего экземпляра Amvera.

1. На VPS установите Python 3.14 и Docker. Разместите чистую копию репозитория
   без локальных `.env`, базы и пользовательских файлов. Установите
   `requirements-deploy.txt` в виртуальное окружение и соберите образ
   `brunohost-worker:1` командой выше. Доверенный процесс Django должен видеть
   Docker и размещать файлы по тем же абсолютным путям, которые видит Docker.
   Доступ к Docker предоставляйте только учётной записи процесса платформы.
2. Используйте `DJANGO_SETTINGS_MODULE=config.amvera` и отдельный
   `AMVERA_DATA_DIR`. Задайте секреты демо отдельно, выставьте
   `DJANGO_ALLOWED_HOSTS=beta.brunolab.ru,localhost,127.0.0.1`,
   `DJANGO_CSRF_TRUSTED_ORIGINS=https://beta.brunolab.ru`,
   `BRUNOHOST_PLATFORM_URL=https://beta.brunolab.ru` и параметры из блока выше
   с `BRUNOHOST_BASE_URL=https://brunolab.online`. До выбора проекта держите
   `BRUNOHOST_ENGINE=disabled`. Инициализируйте базу через
   `python manage.py migrate --noinput` и соберите статику через
   `python manage.py collectstatic --noinput`. Запустите Daphne под надзором
   systemd на `127.0.0.1:8080`, чтобы внешний трафик шёл через HTTPS-прокси.
   Прокси должен сохранять Host и перезаписывать X-Forwarded-Proto.
3. Создайте один проект в бета-лаборатории. До открытия доступа к серверной
   публикации задайте `BRUNOHOST_BACKEND_PROJECTS=<UUID проекта>` и
   `BRUNOHOST_MAX_RUNNING=1`, переключите `BRUNOHOST_ENGINE=docker` и перезапустите
   сервис. Если список задан, остальные проекты не могут
   публиковать серверные версии и их прежние серверные ссылки не обслуживаются.
4. Опубликуйте сгенерированную версию. Для одного демо достаточно создать
   A-запись для выданного `h….brunolab.online` и выпустить обычный HTTPS-сертификат
   на этот адрес. Wildcard DNS и сертификат нужны при автоматической выдаче
   следующих адресов. Поддомены сайта и бета-лаборатории ведут к тому же прокси.
5. На Linux проверьте реальный Docker-исполнитель командой
   `BRUNOHOST_TEST_DOCKER=1 python manage.py test founder.test_hosting.HostedRuntimeTests`.
   После настройки DNS откройте выданную HTTPS-ссылку без входа в BrunoLab,
   запишите данные через форму и проверьте их после перезапуска исполнителя.

## Данные и жизненный цикл

`HostedSite` хранит отдельную выбранную версию, активность и адрес.
`BRUNOHOST_ROOT/<slug>/app/data/data.sqlite3` — база посетителей. Она не копируется
из предпросмотра; сохраняется при обновлении версии, перезапуске и снятии сайта
с публикации. При неудачном запуске база восстанавливается из SQLite backup,
публичная версия не меняется. Разрушительный код миграций модели по-прежнему может
изменять собственную базу сайта: перед значимыми обновлениями нужны внешние backups.
Снятие с публикации останавливает исполнитель и возвращает 404 посетителям.
После перезапуска платформы исполнитель запускается по первому запросу.

Изолированные сайты не видят сессию/авторизацию платформы. Гость получает только
`lab_*` cookies своего приложения; cookies без Domain, HttpOnly, SameSite=Lax,
Secure на HTTPS. Изменяющие запросы требуют точного Origin сайта. CSP запрещает
внешнюю сеть, iframe-embedding и service workers. Ограничены тело запроса, ответ,
время ожидания и частота запросов. Служебный health endpoint посетителям недоступен.

Это начальный хостинг для тестирования, без биллинга, покупки доменов, квот диска
и автоматического масштабирования. Одновременно работает до MAX_RUNNING сайтов;
при достижении лимита новый серверный сайт получит понятную ошибку. Для постоянного
публичного сервиса нужны ещё мониторинг, ротация логов/backup и общие квоты ресурсов.

## Вотермарка

Все опубликованные HTML-страницы получают фиксированную ссылку «Сделано в BrunoLab»
по центру нижнего края окна (12px с учётом safe-area). При наведении и фокусе она
подчёркивается; открывает платформу в новой вкладке с noopener/noreferrer.
Она добавляется только в публичный HTTP-ответ: версии, скачиваемые исходники,
предпросмотр лаборатории, JSON API, CSS и JS не меняются. Повторной публикации
не требуется. Для адреса назначения можно задать BRUNOHOST_PLATFORM_URL;
локально по умолчанию это http://127.0.0.1:8000/, в production — адрес Mini App
или текущий публичный домен BrunoLab. При смене домена установите переменную явно.

## Временные ссылки Amvera (2026-10-30)

`BRUNOHOST_PATH_MODE=1` включает только статические сайты по
`BRUNOHOST_BASE_URL/sites/<slug>/`. В config.amvera режим включён, базовый URL
берётся из TELEGRAM_MINI_APP_URL при отсутствии отдельного домена.
Для серверной беты используйте один Linux-сервер с доступом к Docker и укажите
`BRUNOHOST_PATH_MODE=0` и отдельный `BRUNOHOST_BASE_URL`. На текущем
контейнере Amvera оставьте временный режим. При выключенном режиме пути
адрес платформы не подставляется как домен публикации.
Запросы перехватываются до sessions/auth/CSRF, неизвестные пути не попадают
в маршруты платформы. HTML имеет CSP sandbox без allow-same-origin, connect-src
и form-action none, workers/frames/внешние скрипты запрещены. Это отдельный
ограниченный режим, а не замена полноценного домена: localStorage, серверные
формы и внешние ресурсы здесь недоступны. Inline JS и CSS работают; страницы
конструктора и загруженные изображения получают ссылки внутри своего slug.
Серверные версии публиковать нельзя. При переходе на отдельный wildcard-домен
режим нужно отключить, старые адреса потребуют перенаправления.
