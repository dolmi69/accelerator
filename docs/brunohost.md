# BrunoHost: публикация из лаборатории

Ветка BrunoHost. Публикация независима от карточки сообщества и её видимости.
В лаборатории выбранную HTML-версию или приложение `generated` можно опубликовать,
обновить и снять с публикации. Адрес вида `h` + 13 случайных букв/цифр сохраняется.
Черновики не обновляют публичную версию автоматически. Посетителю аккаунт BrunoLab
не нужен. Старые версии с готовыми Django-модулями пока не публикуются: интерфейс
объясняет ограничение, вместо того чтобы выдавать макет за рабочее приложение.

## Локально

`BRUNOHOST_BASE_URL=http://localhost:8000` (по умолчанию при DEBUG).
Адреса `h….localhost:8000` открываются в Chrome без редактирования hosts.
Django остаётся доступен на `127.0.0.1:8000` и `localhost:8000`.
На macOS серверный код запускается через deny-by-default `sandbox-exec`.
Для других ОС автоматического небезопасного запуска нет.

## Подключение в интернете

Нужны отдельный домен для пользовательских сайтов (например `brunohost.example`),
wildcard DNS `*.brunohost.example` на сервер и wildcard HTTPS-сертификат.
Домен приложения BrunoLab и домен BrunoHost должны быть разными. Публикация по пути
на основном домене намеренно не используется. Основные cookies оставлять host-only,
не задавать общий SESSION_COOKIE_DOMAIN/CSRF_COOKIE_DOMAIN.

Переменные сервера:

```
BRUNOHOST_BASE_URL=https://brunohost.example
BRUNOHOST_ROOT=/data/brunohost
BRUNOHOST_ENGINE=docker
BRUNOHOST_DOCKER_IMAGE=brunohost-worker:1
BRUNOHOST_MAX_RUNNING=5
DJANGO_TRUST_PROXY_HTTPS=1
```

Включать доверие к X-Forwarded-Proto только за своим proxy, который перезаписывает
этот заголовок. Не открывать Django напрямую из интернета.

Сборка подготовленного образа на Linux-сервере с Docker:

```
docker build -t brunohost-worker:1 -f deploy/brunohost/Dockerfile .
python manage.py migrate
```

Reverse proxy передаёт wildcard-запросы тому же Django-процессу, сохраняя Host и
выставляя `X-Forwarded-Proto: https`. Ограничить тело запроса 1 МБ и настроить
серверные лимиты соединений. `ALLOWED_HOSTS` основного приложения не расширять до
`*`: middleware BrunoHost самостоятельно проверяет хост до авторизации и маршрутов.
Не отдавать файлы BRUNOHOST_ROOT через nginx/WhiteNoise.

Статические сайты не требуют исполнителя. Для серверных нужен доступ доверенного
процесса к Docker и указанному образу. Контейнер каждого сайта: без сети и портов,
rootfs read-only, без capabilities, no-new-privileges, 256 МБ памяти, 0.5 CPU,
32 процесса. HTTP передаётся по отдельному Unix-сокету, который доступен только
этому контейнеру и серверу. Docker socket и окружение BrunoLab внутрь не передаются.
На текущей Amvera установка Docker внутри web-контейнера не предполагается:
потребуется подходящий отдельный сервер/исполнитель и домен. Текущий production
не обновлялся; без подключения исполнителя серверная публикация отключена.

## Данные и жизненный цикл

`HostedSite` хранит отдельную выбранную версию, активность и адрес.
`BRUNOHOST_ROOT/<slug>/app/data/data.sqlite3` — база посетителей. Она не копируется
из предпросмотра; сохраняется при обновлении версии, перезапуске и снятии сайта
с публикации. При неудачном запуске база восстанавливается из SQLite backup,
публичная версия не меняется. Разрушительный код миграций модели по-прежнему может
изменять собственную базу сайта: перед значимыми обновлениями нужны внешние backups.
Снятие с публикации останавливает исполнитель и возвращает 404 посетителям.
После перезапуска платформы исполнитель запускается по первому запросу.

Изолированные сайты не видят сессию/авторизацию платформы. Гость получает только
`lab_*` cookies своего приложения; cookies без Domain, HttpOnly, SameSite=Lax,
Secure на HTTPS. Изменяющие запросы требуют точного Origin сайта. CSP запрещает
внешнюю сеть, iframe-embedding и service workers. Ограничены тело запроса, ответ,
время ожидания и частота запросов. Служебный health endpoint посетителям недоступен.

Это начальный хостинг для тестирования, без биллинга, покупки доменов, квот диска
и автоматического масштабирования. Одновременно работает до MAX_RUNNING сайтов;
при достижении лимита новый серверный сайт получит понятную ошибку. Для постоянного
публичного сервиса нужны ещё мониторинг, ротация логов/backup и общие квоты ресурсов.
